# TD-OHD 项目开发规范

## 一、项目目标

TD-OHD 是一个持续发展的综合人类图应用。
个人出生图、行运、关系分析、Penta、Wa 和知识资料库，应当构成统一的产品体系，而不是彼此孤立的多个功能。
项目长期坚持：
统一、复用、准确、清晰、可维护、可扩展。
这些规范是开发原则，不是对现有代码实现方式的永久冻结。

## 二、架构与复用原则

### 2.1 开发前检查

新增功能前，应检查现有项目是否已有：

- 相似页面
- 可复用组件
- 共用渲染函数
- 弹窗基础设施
- 样式与设计变量
- 多语言文案
- 专业术语映射
- 知识资料接口
- 数据模型
- 事件与状态管理
- 对应测试

尽量在已有架构上扩展。

### 2.2 合理复用

可以直接使用现有实现，也可以提取共用组件。
对于确实不同的功能，可以独立实现。
例如：
普通闸门与 Penta 闸门可以共享标题、名称、基础资料和阅读栏目。
但个人激活与群体激活属于不同业务数据，不应强行混成一种计算机制。

### 2.3 避免过度抽象

不是所有相似代码都必须抽象成共用组件。
如果两个功能只有少量外观相似，但实际行为完全不同，保持独立可能更合理。
抽象应服务于一致性和长期维护，而不是单纯减少文件数量。

## 三、统一 UI 设计

### 3.1 共用视觉体系

相同类别的组件应尽量具有一致的：

- 字体层级
- 内外间距
- 圆角
- 边框
- 阴影
- 背景
- Hover、Focus 和选中状态
- 滚动行为
- 手机适配

已有出生图和行运图的成熟组件应作为重要参考。

### 3.2 现有实现参考

以下为当前已存在的重要实现，不要求永久保持这些文件名：

- src/styles.css：基础布局、卡片、弹窗和标题样式
- src/lib/detail-dialog.js：详情弹窗生命周期
- src/lib/bodygraph-detail-layout.js：出生图与行运详情布局
- src/lib/shared-object-details.js：共用闸门、通道阅读内容
- src/lib/gate-lenses.js：闸门资料栏目切换
- src/views/chart.js：出生图交互
- src/views/reference.js：资料库展示
- src/features/transit-timeline/：行运与时间轴布局交互

开发类似功能时应优先查阅这些实现。

### 3.3 弹窗规范

操作弹窗与阅读详情弹窗可以采用不同内容结构，但应共享一致的视觉规范和基础交互。
重点统一：

- 标题
- 关闭与返回按钮
- 表单样式
- 内容间距
- 错误提示
- Esc 关闭
- 焦点管理
- 点击遮罩行为
- 手机适配
- Skin 配色

若目前缺少共用操作弹窗基础层，可以适当抽取。
不要让每个功能自行实现一套完整的弹窗系统。

### 3.4 卡片与滚动

滚动容器必须合理处理上下边缘。
避免：

- 卡片滚动时突然被硬裁切
- 阴影或焦点边框被遮挡
- 不必要的嵌套滚动条
- 切换内容后滚动位置异常重置
- 短屏幕下内容无法访问

左侧固定、右侧滚动和自然页面滚动都可以使用，应根据具体页面选择。
不强制使用渐变遮罩等装饰手段；优先解决实际布局问题。

## 四、Skin 与设计变量

### 4.1 统一来源

Skin 注册表：
src/lib/skin-registry.js
对应 Skin 样式：
src/styles/skins/
新增组件必须服从已有 Skin 语义系统。

### 4.2 变量使用

优先使用对应的语义 CSS Token。
常见例子：

- --bg
- --bg-elevated
- --bg-sunken
- --text
- --text-secondary
- --text-tertiary
- --border
- --border-subtle
- --accent
- --accent-strong
- --accent-soft
- --accent-on
- --focus
- --shadow-sm
- --shadow
- --shadow-lg
- --hd-graph-panel-bg
- --hd-graph-panel-border
- --hd-detail-bg
- --hd-detail-border

人格、设计、行运、关系、回路等颜色，应使用其对应的专用语义 Token。
不能一律用普通强调色代替。

### 4.3 新增变量

当现有变量确实无法满足新的语义需求时：
先检查，再新增，并纳入集中管理。
需要验证各 Skin 的显示效果和文字对比度。
不要求所有场景只有一种颜色，但要求颜色有明确语义。

### 4.4 Skin 验收

涉及视觉修改时，应检查：

- 明亮 Skin
- 深色 Skin
- 高对比度模式
- 按钮和文字可读性
- 选中、悬停、焦点、禁用状态
- 手机端

项目以后新增 Skin，也应尽量通过现有 Token 机制自动兼容。

## 五、多语言与专业术语

### 5.1 普通文案

通过 src/lib/i18n.js 和现有语言资源管理。
支持当前三种语言：

- 简体中文 zh-CN
- 繁体中文 zh-Hant
- 英文 en

不要把中文或英文直接写死在需要翻译的通用组件内。
用户自己输入的人名、团队名称等不自动翻译。

### 5.2 人类图术语

统一通过 src/lib/vocabulary.js 等词汇体系获取。
包括：

- 闸门名称 gateName()
- 易经卦名 hexagramName()
- 通道名称 channelName()
- 中心名称 centerName()
- 行星名称 planetName()
- 爻线名称 lineName()
- 回路 circuitName()
- 回路组 circuitGroupName()
- 类型 typeName()
- 策略 strategy()
- 权威 authorityName()
- 人生角色 profileName()

如缺少需要的专业术语，应扩展统一词汇体系，而不是单独建立另一份名称映射。

### 5.3 对象身份

内部使用稳定编号和 ID。
闸门、通道、中心、人物和团队不能依靠翻译后的名称进行匹配。
这样未来修改术语、切换语言或添加资料跳转时，不会影响业务逻辑。

### 5.4 术语交互扩展

未来可能为术语增加：

- 点击查看说明
- 跳转知识资料库
- 查看关联对象
- 展示上下文解释

现有实现应尽量保留这种扩展能力。
但不要求现在就让所有术语都变成可点击组件。

## 六、统一知识资料

普通闸门、通道、中心及其他基础资料必须同源。
例如 Penta 闸门详情可以包含：

1. 当前群体激活。
2. Penta 专属解读。
3. 原有闸门资料。

其中原有闸门资料必须共用现有内容接口。
不同业务可以增加专属分析，但不应复制一份普通解读。
资料来源、审核状态、证据记录等保留在知识层。
未经验证的机制不能伪装成确定结论。

## 七、数据、状态与计算

### 7.1 显式数据上下文

共用组件通过参数或明确的上下文接收数据。
不能因为使用同一个闸门弹窗，就自动读取当前出生图的数据。

### 7.2 稳定 ID 与存储

人物编辑应保持原有稳定 ID。
修改出生信息时正确更新相关计算及缓存。
不得因为 UI 重构破坏已保存的关系图、团队和 Penta 分组。

### 7.3 计算逻辑保护

普通界面重构不应改变：

- 天文计算
- 闸门、爻线等数值
- 行运计算
- 关系机制
- Penta 拓扑及结构状态

真正需要修改计算时，必须作为独立事项审计和测试。

## 八、交互与可访问性

统一处理：

- Escape 关闭
- 返回
- 焦点恢复
- 键盘导航
- 触屏操作
- 弹窗焦点管理
- 滚动位置
- 加载和错误反馈
- Reduced Motion

避免同一功能多次绑定事件或退出页面后遗留无效状态。
手机可以采用不同布局，但不能丢失核心信息。

## 九、维护与质量检查

开发时优先小范围、可验证的修改。
不随意增加依赖。
组件替换后，应检查是否存在已废弃的 CSS、事件处理或重复实现。
每次 UI 相关任务应检查：

- 是否复用了已有能力
- 是否存在重复组件
- Skin 是否正确
- 多语言和术语是否统一
- 数据是否隔离
- 手机和桌面是否正常
- 是否产生功能退化

按项目既有约定执行构建、预览和测试。
用户体验验收阶段不需要每次都全量回归，但不能把未执行的测试声称为通过。

## 十、规范的持续更新

以上规范是长期指导原则。
未来允许：

- 调整项目结构
- 重构公共组件
- 替换过时实现
- 新增 Skin Token
- 扩展术语和资料系统
- 改善交互及可访问性

规则不应阻碍合理创新。
但新的实现应使系统更加统一，而不是重新产生彼此独立的基础设施。
